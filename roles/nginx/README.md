
# Configure nginx

- Configures nginx based on a template
- Assumes dehydrated, https and redirects all http to https
- Provides a couple of simple website security options

## Example config:

```
nginx:
  vhosts:
    vhost.example.com:
      cookie_auth:
        user_domain: example.com
      locations:
        /:
          cookie_auth: true
          cors:
            origin: "https://pauls-donuts.com"
          location_type: proxy
          proxy: http://localhost:1234
          security_headers:
              csp: "default-src 'self' 'unsafe-inline' 'unsafe-eval' *.tmp.example.com"
      template_type: generic
```

For each virtual host:
- Configures dehydrated with that hostname
- uses the VHOST.template_type field to determine the jinja template to use
  as a base for this site (type-${type}.conf.j2)

- Optionally deploys some files and dirs to assist with htpasswd and/or
  cookie_auth.  The nginx template must also read the relevant variables
  and adjust its config

# vhost template_type values

type        | Description
----------- | -----------
generic     | A generic template intended for most general use cases
grafana     | A reverse proxy specifically for Grafana
jitsi       | For jitsi (overrides the package installed config)
jupyter     | A reverse proxy specifically for Jupyter

Each vhost may have configuration keys other than the `template_type:` that are
supported by that template.

## generic

A generic template, providing SSL and optionally authentication and CORS
origins headers.  Will config each location defined and allow the location to
be one of several different types.

Additional config keys supported:
- `cookie_auth`
- `htpasswd`
- `logsuffix`
- `proxy`
- `security_headers`

```yaml
nginx:
  vhosts:
    vhost1.example.com:
      locations:
        /:
          location_type: proxy
          proxy: http://localhost:1234
      template_type: generic
```

### port

Set the TCP port that this vhost needs to listen with.  If unset, defaults to
port 443

End users should always be accessing the vhost using the standard port.  The
reconfigurable port is for environments where there is a upstream proxy or
similar.

Thus, any automatic redirects generated by nginx will not use this custom
port.

### healthy

It is expected that many things will expose or want a health endpoint, this
implementation hardcodes it to $location/-/healthy, with the expected usual
case being something like https://vhost1.example.com/-/healthy

Inside the location config there is an optional `healthy` key that defines how
the healthy url is provided.

Either `healthy: static200` to always return 200 or `healthy: proxy` to send
the healthy request to the proxied service (without any auth applied)

### location_type

type       | Description
---------- | -----------
proxy      | Proxies requests
return     | Generate custom return codes - like redirect
staticsite | Serves up location.root, with optional try_files_redirect
upload     | Provides a webdav compatible upload endpoint
websocket  | Similar to the proxy type, but with additional websocket config

#### proxy

```yaml
nginx:
  vhosts:
    my_website.example.com:
      locations:
        /:
          location_type: proxy
          proxy: localhost:8080
          proxy_set_header:
            name: val
      template_type: generic
```

Where `proxy` is required and is the server for this location.
`proxy_set_header` is optional and contains a list of headers to add to the
request.

#### return

```yaml
nginx:
  vhosts:
    example.com:
      template_type: generic
      locations:
        /:
          location_type: return
          return: 301 https://www.example.com $request_uri
```

Configured this location with a specific return code.  Mainly useful for
providing redirects - as in the above example.


#### staticsite

A simple static location.  There is no nginx caching of the static files
as it is expected that this will be handled in a cdn if needed.

```yaml
nginx:
  vhosts:
    my_website.example.com:
      locations:
        /:
          location_type: staticsite
          root: /srv/www/my_website
          try_files_redirect: /index.html
      template_type: generic
```

Can use either root or alias, with the usual nginx definitions

Also supports:
- autoindex (boolean)
- types (dictionary used to provide an nginx types{} resource)

#### upload

Provide a simple way to upload files into the webserver.
Originally designed for collecting the outputs of CI build systems.

Recommended that htpasswd be turned on!

```yaml
nginx:
  vhosts:
    my_website.example.com:
      locations:
        /upload:
          location_type: upload
          alias: /var/www/upload
          htpasswd:
            realm: "The realm"
            user_tag: tag
      template_type: generic
```

## Grafana

A reverse proxy specifically for Grafana

Supports no additional configuration keys.

```yaml
nginx:
  vhosts:
    grafana1.example.com:
      security_headers:
        csp: "worker-src 'self' 'unsafe-inline' 'unsafe-eval' blob:"
      template_type: grafana
```

# Use of the additional configuration keys

## `cookie_auth`

- Deploys some helper html
- The template then configures:
    - Each visitor gets a unique cookie assigned to them
      (With 128bits of data, this cookie is hard to brute force, but
      it is not particularly "fully random", so care should be still taken
    - If the visitor's cookie is present as a filename in the filesystem,
      then that visitor is considered granted access.
    - if not granted access, the user is redirected to a page showing the
      cookie (and asking them to make a helpdesk request)
- The cookie_auth.user_domain value allows the same user id cookie to be
  used for multiple hosts and vhosts

Given a cookie of uid=aabbccddeeffgghhiijjkk==, the browser with that cookie
can be granted access by creating a file with the name:
    /etc/nginx/cookie_auth/uid=aabbccddeeffgghhiijjkk==.txt

Usually the contents of the file will be some short identifying text

## `default_site`

This role will also deploy some config to catch all the requests that are not
handled by a defined vhost entry.

There is intentionally only a very small amount of config that is possible for
the default site.

```
nginx:
  default_site:
    http_port: 10123
    https_port: 10456
```

Since more complex hosting situations may have other services listening on the
default ports (80 and 443) it is possible to change them.

## `htpasswd`

This is intended for simplistic site protections, not a comprehensive auth
system.

- Database of users is defined under nginx.htpasswd
- Enabled for a location by setting "htpasswd:" in the location config
- The template adds HTTP Basic auth to the nginx config

If the `htpasswd:` config item has contents, it is a dictionary of
dictionaries of login names and crypted htpasswd values.  It is expected that
defining htpasswd items in the host vars like this is used for service
accounts.

(the `htpasswd` CLI tool can be used to create the hashed passwords,
on Debian this can be installed via the `apache2-utils` package)

```
PW=`apg -m20 -n1`
echo "Create Dashlane for user with $PW"
htpasswd -nb htpasswd "$PW" |sed -e's/:/: /'
unset PW
```

```
nginx:
  htpasswd:
    a_name:
      serviceacct1: $apr1$kajsdhflkasjdhflkasjdhfklasdjh
      serviceacct2: $apr1$a;soekjrfvnqwepruinweiq;weldrj
```

### `logsuffix`

If it is desired to split out a locations logs separately, then define this as
true to create logs for this location.  The filename will be based on the
vhost name and location.

```yaml
nginx:
  vhosts:
    my_website.example.com:
      locations:
        /testsite:
          [blah blah other config]
          logsuffix: true
```

The above would result in the log files:
- /var/log/nginx/my_website.example.com__testsite_access.log
- /var/log/nginx/my_website.example.com__testsite_error.log

And would configure the prometheus nginx log exporter with the log file using
the tag "vhost=my_website.example.com/testsite"

### `proxy_protocol`

Boolean to enable the use of proxy_protocol for incoming connections

### `real_ip_from`

Array of subnet addresses to use to set the proxy forwarded for trust.

```
nginx:
  real_ip_from:
    - 10.1.2.0/24
```

## `security_headers`

The security headers refers to a fairly standard set of headers, minus any
headers that manage SSL

```yaml
nginx:
  vhosts:
    my_website.example.com:
      locations:
        /:
          [blah blah other config]
          cors:
              origin: "https://my-other-site.example.com"
          security_headers:
              csp: "default-src 'self' 'unsafe-inline' 'unsafe-eval' *.example.com"
```

The `security_headers` stanza configures a mostly premade block of security
headers added to the system. In the above example, `enabled` and `cors_origins`
also match the calculated defaults so are not strictly necessary

The CSP can be fully declared or otherwise it will default to `default-src 'self' 'unsafe-inline' 'unsafe-eval'`

If you want to turn the entire block off, set `security_headers.enabled: false`
this is useful if the proxied backend is providing the security headers itself
and you don't want to override the backend's headers. (TODO: nginx can be set
to only fill in headers that don't already exist, but that's a more complex
method using maps)

## Basic Auth and http OPTIONS verb

An 'options stanza' is intended to go into a `location / {}` nginx block and
allows for a precalcuated response to an OPTIONS request for Basic Auth
protected locations

CORS and Basic Auth do not play together nicely for browser javascript. This
cannot be replicated with curl or doing a GET by putting the URL in the browser
url bar directly - the problem is solely within the way browser javascript
functions. It does an OPTIONS request before doing a GET, and ends up in a
catch-22 where it needs Basic Auth to get CORS and needs CORS to get Basic Auth

So we supply this precalculated block which does not require Basic Auth
to retrieve

```yaml
nginx:
  htpasswd:
    root:
      serviceacct1: $apr1$kajsdhflkasjdhflkasjdhfklasdjh
      serviceacct2: $apr1$a;soekjrfvnqwepruinweiq;weldrj
  vhosts:
    my_website.example.com:
      locations:
        /:
          cors:
            credentials: 'true'
            headers: "DNT,User-Agent,X-Requested-With,If-Modified-Since,Cache-Control,Content-Type,Range,Authorization"
            max_age: "1728000"
            methods: "GET, POST, OPTIONS, PUT, DELETE"
            origin: "https://my_website.example.com"
          proxy: http://localhost:8080
          security_headers:
            csp: "default-src 'self' ws: data: 'unsafe-inline' 'unsafe-eval' *.example.com"
            enabled: false  # this means security headers are disabled for regular requests
          location_type: proxy
          htpasswd:
            realm: "Password Protected"
            user_tag: root
      template_type: generic
```

If your security_headers have been disabled, for example to allow the backend
to manage headers, you can re-enable them just for OPTIONS requests in a Basic
Auth location by defining `cors:`. You should probably define at least one CORS
header as well.
